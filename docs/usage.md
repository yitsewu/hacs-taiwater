# 台灣自來水公司：Home Assistant／HACS 整合

版本：`0.4.0`，初版測試套件，最低 Home Assistant `2026.9.1`。適用台灣自來水公司水費查詢；不適用臺北自來水事業處。

輸入水號與戶名後，由 HA 直接查詢官方網站，提供帳單、歷史分攤、排程與狀態感測器。OCR 與模型已內建，全部在使用者自己的 HA Core 執行，不需附加元件、container、OCR 網址或手動下載模型。 [English installation guide](README.en.md)。

## 安裝

可透過 HACS 自訂儲存庫或 ZIP 安裝。

1. HACS：「自訂儲存庫」加入 `https://github.com/yitsewu/hacs-taiwater`，類型選 Integration，下載後依正常流程重新啟動 HA。也可使用 ZIP，將完整 `custom_components/taiwater`（含 `models`）放入 HA `/config/custom_components/`。
2. 「設定 → 裝置與服務 → 新增整合 → 台灣自來水公司」，填水號、戶名及顯示名稱。首次查詢自動載入內建模型。
3. 在整合選項調整排程、歷史期數、分攤方式及碳排係數。無需任何額外 OCR 安裝步驟。

相依由 HA 的 requirements 機制處理：`numpy==2.3.2`、`Pillow==12.3.0`，與驗證版本 HA Core 2026.9.1 的 constraints 相同；不呼叫 pip、不改 HA 全域環境或 CPU 設定。安裝依賴需要正常套件來源連線；模型已隨整合提供，辨識時不連線模型站或第三方 OCR。

## 設定

| 設定 | 預設／行為 |
| --- | --- |
| 水號、戶名 | 必填；水號保留前導零，允許顯示用連字號 |
| 顯示名稱 | 台灣自來水公司；可改為房屋名稱，多水號分別新增整合 |
| 自動查詢 | 每週一 09:00，使用 HA 設定時區 |
| 查詢排程 | 每日、每週或每月指定日期／時間；月末不存在的日期使用該月最後一天 |
| 首次歷史期數 | 0＝原站提供的全部帳期；也可設定最近 N 期 |
| 分攤方式 | 預設按涵蓋月份平均分配；另可選按實際計費期間天數分攤 |
| 碳排係數 | 未設定；單位 kgCO2e/m³，設定時須填來源／適用年份 |
| 進階 OCR 網址 | 選項內留空＝內建本機 OCR；只有刻意選用外部備援時才設定 |

排程更新只補齊尚未保存的帳期，並重新查最新一期。「補抓歷史」會重新查設定範圍內的帳期，用於回填或更新修正過的舊帳單。原站日後移除舊帳期，不會刪除已保存的資料。

## HA 提供的資料

- 最新帳期、用水度數、原始應繳總金額、原站費用細項及可取得的日期。
- 最新有資料月份的分攤用水／費用／碳排、年度已取得資料合計與涵蓋月份數。
- 上次查詢時間、上次成功時間、上次失敗時間、下次排程時間。
- 查詢結果、OCR 辨識結果、原站驗證結果、錯誤碼、已匯入與可查帳期數、歷史完整性與統計寫入狀態。
- 「立即查詢最新一期」、「補抓歷史」、「重建長期統計」按鈕與「自動查詢」開關。
- 若原站提供付款狀態就顯示；沒有資料時為未知，不推測已繳或未繳。

OCR 的 `success` 只表示辨識出格式有效的文字，不等於原站接受。原站明確拒絕驗證碼時，會同時出現「OCR 成功」與「驗證失敗」。網路失敗或回應不明時，不捏造驗證結果。完整查詢失敗不更新最後成功時間；歷史部分失敗保留已取得的有效帳單並標示 `partial`。

## 查詢紀錄與指定帳期補抓

在 HA「開發者工具 → 動作」可使用以下動作；也可加入自己的 script／自動化。`config_entry_id` 在介面選擇台水帳戶，YAML 範例則替換為該整合的設定項目 ID。

```yaml
action: taiwater.get_query_history
data:
  config_entry_id: YOUR_CONFIG_ENTRY_ID
  limit: 25
response_variable: query_history
```

每個帳戶保留最近 **100 次**查詢，最新紀錄在前。記錄查詢 ID、觸發方式（setup／initial／schedule／button／manual／action）、操作（initial／latest／history／month）、指定帳期、開始／完成時間、耗時秒數、結果、OCR 結果、台水驗證結果、固定錯誤碼與取得帳單數。`fetched_count` 是取回數量，不代表通過格式檢查或新增的帳單數。

紀錄隨 HA 重啟保留；未完成的查詢標成 `interrupted`，完成時間是啟動時辨識中斷的時間，未知耗時留空。首次設定匯入的結果也會記錄，但未量測的耗時留空。升級前的逐次歷程無法回補。無效輸入或忙碌時拒絕的請求尚未開始查詢，不增加紀錄。讀取紀錄不連線台水，也不保存姓名、水號、驗證碼文字／圖片、Cookie 或原始錯誤內容。

```yaml
action: taiwater.query_month
data:
  config_entry_id: YOUR_CONFIG_ENTRY_ID
  month: "2026-08"
response_variable: queried_bill
```

指定的是**原站帳期**，不是分攤後的月份。可從 `taiwater.get_history` 的 `available_months` 取得最近已知清單。此動作重新建立工作階段、執行 OCR／驗證，再取得指定帳期；原站驗證流程可能先回傳預選帳期，但只保存要求的那一期。不需要重抓其他歷史，也不改動下次排程。

回應包含 `query` 查詢紀錄及 `bill` 正規化帳單；`response_variable` 可省略。同帳期更新後會重建本整合的分攤統計，不重複累加。不存在的帳期回報 `month_unavailable`；查詢失敗保留原帳單，原因可由查詢紀錄讀取。OCR 失敗沿用既有人工查詢備援。

## 費用、碳排與歷史統計

整合內建「台灣自來水公司 總用水量」，安裝並取得帳單後即自動提供，無須另外建立 helper、template sensor 或自動化；在 HA 能源設定選取這筆用水統計即可。統計另提供「總費用」及「總碳排量 kgCO2e」，所有名稱調整保留原 statistic/entity ID。自訂帳戶顯示名稱時，會使用「顯示名稱 總用水量」以區分多個帳戶。

台水帳單通常兩個月一期。預設將整期用水量與費用平均分配到帳單涵蓋的兩個月，例如 60 度、600 元分為每月 30 度、300 元。這是帳單分攤估算，並非每月實際抄表量；非兩個月的帳期依實際涵蓋月份平均分配。 既有帳戶沿用先前選擇；舊版未明寫選項的帳戶升級時明確保留舊的按日分攤，不套用新預設。可到整合選項的「排程與計算設定」將「帳期跨月配置方式」改為「跨月平均分配」。

原始帳單始終保留。月度／日度／小時數值都是**帳單分攤估算**，不是即時水表讀值，也不是付款日期的現金流。

- 原站「本期計費用水期間」包含開始與結束日。按日模式依各月實際涵蓋天數分攤；等額模式先在涵蓋月份之間等分，再分配到該月涵蓋日期。
- 費用直接分攤原始總額，不重新套用單月水價。加退款可為負數，細項不重複加入總額。
- 缺少計費日期時，月度列表使用「帳單月份＋前一月」的明確估算；不偽造實際抄表日期，也不為這部分產生日度長期統計。
- 碳排優先使用原站明確提供的 kgCO2e 數值；沒有時才套用使用者設定的係數。未設定係數顯示未知。係數應註明來源、年份、供水範圍；不代表家庭熱水、污水處理等全部碳排。
- 年度合計僅涵蓋已取得資料。尚無帳單的月份不補零；不得將部分年度合計當作完整年度。
- 不為「每期用量」設定不適用的 `total_increasing`。整合另以 `taiwater:<entry_id>_water`、`_cost`、`_carbon` 保存分攤長期統計，其中費用固定 TWD，不隨 HA 顯示幣別變成其他貨幣。
- 可在 HA 能源設定選取對應的外部水量統計及費用統計。碳排提供獨立統計，不冒充能源面板的電網碳強度。實際 UI 可選擇性以相應 HA 版本驗收為準。
- 同帳期以最新成功結果更新，不重複累加。區間重疊或格式不符時拒絕寫入。修正歷史或分攤設定後，從已保存帳單重建**本整合自己擁有的三個統計 ID**；不清除其他整合資料。

## 背景寫入與疑難排解

`0.3.0` 起，帳單保存及查詢紀錄完成後就回傳，長期統計由獨立背景工作寫入。查詢耗時不再包含 Recorder 寫入；能源圖表需等「長期統計狀態」變成「已完成」才代表寫入並讀回驗證通過。「上次統計寫入完成」與「上次統計寫入耗時」分別提供時間及秒數。

- 查詢按鈕在台水查詢期間暫時不可用。自動化同時查詢會收到「已有查詢正在進行」提示，不新增失敗紀錄。
- 背景統計不占用台水查詢鎖。寫入期間收到多次更正，會合併等待中的版本，接著以最新已保存帳單重建。
- 統計失敗時帳單與查詢結果仍保留。「重建長期統計」按鈕可直接重試，不連線台水、不執行 OCR、不改動排程或查詢紀錄。
- 同次載入期間，相同分攤結果不重複寫入；手動重建可強制修復。重新載入會從保存帳單在背景重新建立統計，沒有以快取指紋假定 Recorder 資料仍存在。
- 大量歷史資料仍需要 Recorder 寫入時間。每日分攤與逐時序列計算已移至 executor，避免阻塞 HA 事件迴圈；這不代表資料庫寫入本身變快。
- 解除載入會等待已開始的查詢及背景寫入結束；不刪除帳單。強制關機後重新載入可從保存資料重建。

升級時先備份 HA，替換 `custom_components/taiwater` 並重新啟動。`0.3.0` 沿用既有 entry、帳單及查詢歷程格式，不需重新填水號或戶名；OCR 附加元件維持 `0.1.1`。

## Cookie 與人工備援

每次新查詢建立自己的 Cookie 工作階段，取得原站驗證碼及 CSRF token。OCR 只處理圖片，HA 使用同一工作階段完成水號／姓名驗證及帳期切換，並沿用原站更新後的 token。使用者不用複製 Cookie。

驗證失敗不無限重試；本次記錄失敗，下次重新建立 session。HA 重啟後 session 不保留。OCR 不可用時，可在設定流程或整合選項的「人工查詢」查看圖片並輸入驗證碼。

驗證碼圖片透過三分鐘失效的隨機能力網址供設定介面讀取，不包含帳戶資料，送出後即失效；不寫入磁碟。對外提供 HA 時應使用 HA 自己的 TLS／登入保護。

## 內建 OCR 的來源、資源與驗證

- 使用 ddddocr 1.5.6 的 `common_old.onnx`（MIT），僅在開發時轉出權重與圖結構。整合內附原授權、來源及 SHA-256；第一次載入驗證兩個檔案完整性，使用 `allow_pickle=False`。模型約 6.8 MB，HACS／ZIP 一併提供。詳見 [模型來源](../custom_components/taiwater/models/source.json) 與 [轉換程式](../scripts/export_ocr_model.py)。
- 執行時只需 NumPy／Pillow，不載入 ddddocr、ONNX Runtime、OpenCV、外部執行檔或自行編譯的 wheel。卷積沿用整数量化；LSTM 使用反量化權重與 float32 activation，與原引擎可能有數值差異，因此以辨識結果驗證，不宣稱逐浮點數相等。
- 模型載入及辨識在 HA executor；全程共享一份模型、串行推論，等待鎖最多 30 秒。載入／推論異常釋放失效模型並等待 30 秒再試；辨識文字不合格式標示失敗，不覆寫帳單。限制圖片 2 MB／400 萬像素，縮放後高度 64、寬度最多 512。
- 不修改 BLAS 執行緒或環境變數；使用單執行緒 NumPy einsum。模型在 HA 行程內快取，多帳戶與重新載入不重複配置。
- 已在未安裝外部 OCR 的官方 HA Core 2026.9.1 容器驗證：Python 3.14.6、musl、amd64／aarch64，使用 HA 的實際 requirements resolver。三組合成字碼皆完全辨識成功；暖機後每張約 0.30–0.34 秒／0.22–0.25 秒。測試行程峰值約 175 MiB（包含 HA Python 行程，不是 OCR 增量用量）。
- 同一 Core image 在 QEMU `qemu64` 的 SSE2／SSE3 基線也通過；模擬推論耗時不能當作實機效能。其他 HA 版本、32 位元架構及硬體尚未驗證，不要求變更虛擬 CPU。
- `OCR 執行方式` 感測器與新查詢紀錄的 `ocr_backend` 顯示 `builtin`／`external`／`manual`。辨識成功、原站驗證接受、查詢成功與統計寫入仍獨立記錄。

舊 OCR 附加元件是選用備援，已安裝者可保留。整合不再自動選擇它；若要刻意使用，僅在進階選項設定其內網 URL。正常安裝與查詢完全不需要它。人工驗證仍可使用。

升級到 0.4.0 保留既有 entry、水號、戶名、排程、分攤偏好、帳單及查詢紀錄；首次安裝的新帳戶預設等額分攤。請先備份 HA，再更新完整整合資料夾並重啟。

## 保存、隱私與回復

水號與戶名存於 HA 原生 config entry；帳單與查詢狀態存於 `/config/.storage/taiwater.<entry_id>`，HA Recorder 保存統計。不把水號、戶名、銀行代繳帳號或地址放入 entity/device ID、診斷下載、程式碼或日誌。

Cookie、CSRF token、驗證碼文字／圖片與原始 HTML 只留在記憶體。OCR 不收水號或戶名；附加元件預設不對外開放連接埠。請將 HA 備份視為含私人設定與帳單的資料保管。

停用排程不會刪帳單；移除整合前請先備份 HA。解除載入不清除保存資料或外部統計。回退版本時恢復已驗證的程式 ZIP 與必要 HA 備份，勿手動修改 Recorder 資料庫。

## 開發驗證

```shell
python -m pip install pytest pytest-asyncio tzdata Pillow ruff
pytest tests --ignore=tests/ha -q
ruff check custom_components tests scripts taiwater_ocr
python scripts/package.py
```

Linux／Python 3.14 的完整 HA 測試使用 `pytest-homeassistant-custom-component==0.13.364`，執行 `pytest tests/ha -v`。CI 同時驗證 HACS 目錄結構、hassfest、OCR container 模型載入與去識別測試。測試不登入真實帳戶，不保存原始帳單。

查詢 parser 由既有本機台水工具整理而來；OCR 依賴透過套件管理器安裝，相關第三方程式遵循原授權。

OCR 附加元件 `0.1.1` 固定 NumPy `2.3.5`，相容未提供 x86-64-v2 指令集的 HAOS 虛擬 CPU；不要求修改 VM CPU 模式。

`0.2.2` 對 `www.water.gov.tw` 的 TLS 憑證鏈缺少 Subject Key Identifier（OpenSSL 86）加入一次相容重試；保留 CA 信任、簽章、效期及 hostname 驗證。不對其他憑證錯誤重試，不修改 HA 全域 TLS 設定。
